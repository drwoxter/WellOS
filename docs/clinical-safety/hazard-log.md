# Hazard Log

Living document. Severity/likelihood are qualitative pending a formal risk
matrix. All hazards refer to the intended future clinical use; the current
system runs on synthetic data only.

| ID | Hazard | Cause | Potential harm | Controls (implemented) | Residual risk / planned |
| --- | --- | --- | --- | --- | --- |
| H-01 | Critical result not acted on | Alert missed, workflow abandoned | Delayed treatment | Loop state machine requires review→notify→close; worklist surfaces open loops; deterministic overdue escalation | Escalation delivery (paging/on-call) not built |
| H-02 | Wrong criticality classification | Threshold error, unit confusion | Missed critical / false alarm | Versioned deterministic rules; UCUM-aware conversion; refusal + DataQualityIssue on unknown units | Rule library review process needed |
| H-03 | AI summary misleads clinician | Model error/hallucination | Wrong clinical impression | A2 autonomy; mandatory human review; citations to source facts; limitations displayed; disclaimer; deterministic rule remains authoritative | Evaluation harness & drift monitoring planned |
| H-04 | AI acts autonomously | Design/regression error | Unauthorized order/prescription | No code path from artifact to clinical action; policy actions for orders require human identity; tests | Keep negative tests in CI |
| H-05 | Duplicate result creates duplicate alerts | Interface replay | Alert fatigue, confusion | Idempotency key unique per tenant; replay returns original ids | — |
| H-06 | Amended result unseen | Correction after review | Decisions on stale data | Amendment preserves history and reopens review | UI diff of amended values planned |
| H-07 | Wrong patient/tenant data exposure | AuthZ defect | Privacy breach, wrong-patient action | Central policy; tenant scoping in all queries; cross-tenant denial incl. break-glass; audit of denials | Postgres RLS planned |
| H-08 | Unauthorized loop closure | Role misconfiguration | Accountability gap | Closure restricted to authorized clinician roles; nurse-closure denial tested | Role review workflow planned |
| H-09 | PHI leakage via AI provider | Misconfigured external AI | Privacy breach | providers `disabled` by default; `WELLOS_ALLOW_EXTERNAL_AI` + `allow_external_ai=false` default; purpose-specific consent gate; HTTPS + exact host allowlist, no redirects, no prompts/transcripts/keys in logs; offline fake fixture only in dev/test builds | Redaction layer before any real provider |
| H-10 | Audit trail gaps | Missed instrumentation | Unaccountable actions | Audit emitted inside the same transaction as state changes | Tamper-evident hash chain planned |
| H-11 | Concurrent edits corrupt loop state | Race between users | Inconsistent state | Optimistic concurrency (`version`), 409 on stale writes | — |
| H-12 | Inaccessible UI blocks urgent action | A11y defects | Delayed response | Semantic tables, labels, `role="alert"`, keyboard operability; WCAG 2.2 AA target | Automated a11y tests planned |
| H-13 | Under-triage of a deteriorating patient | Priority set too low; AI proposal trusted over findings | Delayed emergency care | Deterministic safety floor (`triage-safety@1.0.0`) from explicit red flags, urgent arrival and abnormal vitals; UI disables and server rejects priorities below the floor; dMind proposals clamped to the floor and never applied without explicit human review | Rules are not a validated triage scale; clinical sign-off, prospective evaluation and reassessment timers required before real use |
| H-14 | dMind triage proposal acts on stale facts | Triage edited after generation | Decision on outdated vitals/flags | Proposal bound to the exact triage version; acceptance of a stale version refused (409); new proposal required | — |
| H-15 | Ready patient not seen | Alert unnoticed, wrong recipient | Prolonged waiting, deterioration | Directed alert to the assigned professional or the facility service queue; re-routing resolves and re-raises; Ready list on dashboard and access board sorted by priority then wait; acknowledgement audited | No escalation timers or paging; alerts are internal only |
| H-16 | Wrong-patient consultation from the worklist | Similar names, stale board | Wrong-patient documentation | Cards show name, identifier, age, reason and facility; start-consultation locks patient and visit and re-checks status/version; encounter header shows safety info | Photo/second identifier confirmation not implemented |
| H-17 | Unauthorized access via care-team routing | Role misconfiguration; assignment to a professional outside the facility | Privacy breach | Care relationship is patient-specific (assignment or encounter), never implied by role; routing restricted to the visit's facility; central policy re-checks every action; capability hints are presentation only | Care-team management UI and periodic assignment review planned |
| H-18 | Risk level misleads prioritisation | Rule threshold error; stale or missing records treated as reassurance | Deteriorating patient deprioritised; alert fatigue | Versioned deterministic rules (`risk-rules.v1`) with every factor explained and linked to its source record; `insufficient_data` is a distinct level and missing/stale data are surfaced per domain, never mapped to `low`; no aggregate numeric score; the overall level is the maximum domain level; snapshots are append-only and reproducible via `input_hash` | Rules are not a validated risk score; clinical sign-off, prospective evaluation of alert burden and a rule-library review process required before real use |
| H-19 | AI risk summary softens a critical signal | Model error; wording that minimises a deterministic finding | Critical risk overlooked | dMind output is aligned to the deterministic assessment before validation (`raised_to_floor` recorded, limitation appended); any residual mismatch is rejected; the UI shows deterministic levels and evidence first and labels the summary AI-generated; proposals are bound to the exact assessment and superseded by a newer one | Evaluation harness and wording review for the fake and future real providers planned |
| H-20 | AI suggestion becomes clinical work without a human decision | Design/regression error | Unreviewed task or order | Suggestions are advisory text; a follow-up task is created only by a confirmed `POST …/confirm` from an authorised professional on an approved, non-stale artifact, is anchored to that professional and artifact, and is audited; no path to orders, diagnoses or prescriptions; negative tests in CI | Keep negative tests as the suggestion set grows |
| H-21 | Insurer projection exposes or misuses clinical data | Over-broad payload; missing consent check; use for coverage or pricing | Privacy breach; discriminatory decision | Separate `risk.projection_read` permission (clinical administrator, `insurer_integration_agent` scope only), operations purpose, active `insurer_risk_sharing` consent, facility and tenant scope; payload limited to levels, versions, review state and record provenance (no names, notes, values); every attempt audited; no pricing, underwriting, coverage, authorization or denial logic exists | Insurer identity, delivery and contractual review belong to the future integration milestone |
| H-22 | Worklist review masks a worsening patient | Acknowledgement outlives the risk it was made for | Missed escalation | Reviews are bound to the level they were made against and reappear as unreviewed when a later calculation raises the level; actions bound to the displayed assessment (`409 assessment_stale`); critical and high always sort first; recalculation happens in the same transaction as the triggering clinical change | No escalation timers; the worklist is a prioritisation aid within the professional's facilities |
| H-23 | Appointment booked for the wrong patient or on the wrong resource | Browser-supplied patient id; stale candidate; catalog/resource drift between matching and confirmation | Missed or wrong care; wasted clinical capacity | Patient identity comes from the authenticated grant for `/api/v1/me` and from the access request (tenant + facility checked) for staff; the hold and the acceptance re-load the offer, its resources and the service inside one transaction with row locks and re-check tenant, facility, service and resource activity; offer acceptance is bound to the offer id, the principal that placed the hold and the optimistic `version`; confirmation shows patient, service, resource(s), facility and time before the final action; every booking writes `appointment_history` and an audit record | Wrong-patient selection by staff before the request is created remains a human control (patient banner in the console); no biometric or wristband check |
| H-24 | Double booking of a professional, room, equipment or vehicle | Concurrent holds/acceptances; multi-resource services; DST or time-zone errors; hold expiry races | Two patients for one slot; cancelled care at the door | PostgreSQL exclusion constraint on `resource_bookings` (`resource_id`, `slot_index`, `tstzrange(starts_at, ends_at)` while `status='active'`) covers holds and appointments alike; multi-resource services book every required resource in the same transaction; a losing concurrent acceptance receives `409 slot_taken`, proven by `concurrent_acceptance_of_the_same_capacity_books_once`, `required_room_is_never_double_booked_across_professionals`; availability is projected per day from local wall time to UTC (`dst_transition_keeps_local_wall_time`); expired holds are released by the worker only after `hold_expires_at` | Capacity > 1 resources rely on correct `slots` configuration; unexpressable constraints (patient travel between facilities) are checked only inside the booking transaction |
| H-25 | dMind ranking hides clinically appropriate access | Model demotes the earliest or clinically indicated option; omits a candidate; invents one | Delayed care; inequitable access | The matcher is authoritative: `appointment-ranking.v1` receives only validated candidate ids and may reorder/explain, never add or remove — unknown ids, missing ids or omitted citations invalidate the artifact and the deterministic order is used; urgency and waiting-time floors are enforced deterministically after ranking (`ranking_must_be_a_permutation_of_supplied_candidates`, `matching_stays_deterministic_when_dmind_is_disabled_or_degraded`); the UI labels the ranking source (deterministic / dMind / synthetic) and shows every candidate with its score decomposition; the patient always sees the earliest valid option; AI disabled or degraded falls back to deterministic order, never to a fabricated response | Ranking quality is not clinically validated; human review of ranking explanations is encouraged but not mandatory for routine bookings |
| H-26 | Personal-calendar data disclosure | Raw `.ics` storage; event titles/attendees retained; calendar read by staff or another patient | Privacy breach beyond scheduling purpose | ICS files are parsed in memory with hard bounds (1 MB, 2 000 events, 400 occurrences/event, 5 000 intervals, 180-day horizon); only normalised busy intervals, time zone, source type and an integrity hash are persisted — never titles, descriptions, attendees, links or the file; import requires active `scheduling_calendar` consent and the patient's own grant; staff never see busy intervals, only the matcher's "patient unavailable" rejection reason; disconnect deletes derived intervals; connect, sync and disconnect are audited (`calendar_import_is_consented_bounded_and_privacy_preserving`, `keeps_only_busy_intervals`, `bounds_are_enforced`, `imported_busy_time_excludes_matcher_candidates`) | Device free-busy sync shares the same minimisation but depends on the client honouring it; no calendar provider OAuth exists (by design) |
| H-27 | Discriminatory no-show scoring | Appointment history used to deny, deprioritise, surcharge or hide options; protected characteristics used as features | Unequal access for vulnerable patients | `confirmation_history` is a soft factor bounded in magnitude and used only to trigger supportive interventions (extra reminders, offering a more convenient slot) — it never removes a candidate, lowers urgency, changes ordering below the fairness floor or exposes a "risk score" to the patient (`no_show_history_never_lowers_score`); protected characteristics are not matcher inputs; the score decomposition is persisted and visible to staff; policy per tenant can disable the factor | Statistical bias audits over real populations are not yet possible (synthetic data only); supportive actions are suggestions, not guaranteed outreach |
| H-28 | Cancellation slot never offered or offered unfairly | Worker outage; eligibility bug; AI reorders below fairness floor; stale consent | Lost capacity; patient who waited longest skipped | A cancellation inside the recovery window creates a `cancellation_events` row in the cancelling transaction; eligibility is deterministic (service, facility, modality, preferences, minimum notice, calendar conflicts, consent, not paused) and persisted with reasons; the base order is urgency then waiting time then preference fit, and `cancellation-recovery.v1` may only reorder within the same urgency band above the floor (`floors_reject_demotion_of_urgent_or_long_waiters`, `recovery_order_must_cover_every_entry_once`); offers are time-limited and decline/expiry advances automatically (`cancellation_offers_the_freed_slot_fairly_and_cascades_on_decline`, `expired_offer_cascades_via_worker_and_exhausts_cleanly`, `concurrent_acceptance_of_one_waitlist_offer_books_exactly_once`); staff overrides require a reason and are audited (`staff_override_requires_a_reason_and_is_bounded_by_scope`); every offer, expiry, acceptance, override and failed race is audited; the workflow is identical with AI disabled | If the worker is down, offers do not expire and the slot is not re-offered until it resumes (runbook alert on worker lag); no SMS/push channel yet, so patients see offers in-app or by e-mail when SMTP is enabled |
| H-29 | Reminder or confirmation never delivered | Adapter disabled or misconfigured; retries exhausted; quiet hours; duplicate deliveries from multiple replicas | Missed appointment; patient attends a cancelled one | Notifications are durable rows claimed with `FOR UPDATE SKIP LOCKED`, delivered idempotently per `(notification_id, channel)`, retried with bounded backoff and parked in `dead` with an audit record; in-app delivery always works; SMTP and the signed webhook are disabled by default and their failure never blocks booking; dead-lettering writes a `notification.dead_lettered` audit record and a PHI-free warning log, and the runbook defines the monitoring query and alert; reminders respect quiet hours and patient channel preferences; subjects and logs carry no PHI (`notifications_are_idempotent_retry_with_backoff_and_dead_letter`) | External delivery depends on tenant configuration; there is no delivery-receipt feedback loop from e-mail providers |
| H-30 | Incorrect seasonal or absence forecast drives harmful capacity decisions | Thin history; wrong operational calendar; model explanation overstating certainty | Capacity removed when demand rises; over-staffing | `capacity-forecast.v1` is deterministic and explainable: expected demand, capacity, gap, uncertainty and contributing factors are persisted; `insufficient_history` is reported explicitly below the evidence threshold (`capacity_forecast_reports_insufficient_history_then_seasonal_pressure`); `capacity-explanation.v1` may only narrate the persisted forecast with cited factors; forecasts recommend — they cannot cancel care, remove availability or change clinical priority; holidays, school breaks, local events and seasonal periods are tenant-configured data, not code | Forecast accuracy is unvalidated; recommended actions still require a human scheduler |
| H-31 | Unauthorised patient representative | Identity claimed from name/birth date/MRN; expired or revoked grant still honoured; catalog/specialty treated as permission | Disclosure of a patient's scheduling data; bookings made without authority | Access to `/api/v1/me/...` derives the patient set only from active, unexpired, unrevoked `patient_access_grants` for the authenticated OIDC subject; grants are created by staff with `patient_grant.manage` after audited verification and record relationship (`self`, `parent_guardian`, `authorized_proxy`), expiry and revocation; requests for a patient outside the grant set return the same `not_found` as a non-existent patient; `patient_representative` has no chart, result, note or risk permission; specialty/profession/catalog membership grants nothing (`self_service_identity_comes_only_from_an_active_grant`, `representative_books_for_one_of_several_dependants`) | Verification of guardianship documents is a staff process outside the system; no self-service grant request flow yet |
| H-32 | Patient location disclosure | Origin or live coordinates stored in clear; read by unauthorised staff; live trail retained after transport | Stalking, safety and privacy harm | Matching uses one-time in-memory coordinates or an approximate area; retained addresses and live coordinates are encrypted with AES-256-GCM under a configured rotation-ready keyring and the capability fails closed in staging/production without one; `scheduling_location` and `transport_coordination` consents are required; location reads need `transport.coordinate` for the specific transport episode and every read is audited; live positions are accepted only in `scheduled`/`en_route`/`picked_up`, expire after `WELLOS_LIVE_LOCATION_TTL_SECS` and are purged by the worker (`transport_requires_consent_encrypts_addresses_and_purges_live_locations`, `transport_fails_closed_without_an_encryption_key`) | Key custody and HSM integration are deployment concerns; transport operators see pickup address by necessity |
| H-33 | Transport failure or unsafe automatic dispatch | Vehicle not actually available; status not updated; AI or rule dispatching an ambulance | Patient stranded; emergency resource misused; delayed emergency care | Vehicles and teams are schedulable resources under the same exclusion constraint; transport requests follow `transport-request.v1` with an accountable operator and pickup window, and status changes notify the patient; `emergency=true` requests require an authorised human (`transport.coordinate`) decision recorded with actor and reason — no dMind operation, worker or rule can create or advance an emergency transport (`emergency_transport_needs_a_human_coordinator_decision`); a failed transport moves the request to `failed`, notifies the patient of the status change and leaves the appointment intact for human rescheduling | WellOS is not an emergency dispatch system; integration with regional emergency services is out of scope |
